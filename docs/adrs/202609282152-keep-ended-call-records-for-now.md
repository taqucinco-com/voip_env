# 通話終了後もcalls/{roomId}を削除せず保持する

## ステータス

承認済み（`docs/adrs/202609271801-call-room-schema-and-signaling-endpoints.md`の影響・トレードオフで先送りしていた「アーカイブ・削除方針」についての決定）

## コンテキスト

`docs/adrs/202609271801-call-room-schema-and-signaling-endpoints.md`では、`calls/{roomId}`を通話終了後も削除せず`status: "ended"`のまま残す設計とし、レコードが増え続ける問題への対処（アーカイブ・削除方針）は将来の検討課題として先送りしていた。

Flutterクライアントの実装を進める過程で、レコードを際限なく残したくないという理由から`endCall`を「`calls/{roomId}`をノードごと削除する」方式に変更することを検討し、一度実装した。しかしこの方式には次の問題があった。

- 通話終了の理由（`endedReason`: `rejected`/`cancelled`/`hangup`）は`end` APIのレスポンスとして**呼び出した本人にのみ**返る
- 受動的に待っている側（発信をキャンセルされた着信者、着信を拒否された発信者など）はRealtime Databaseの`calls/{roomId}`を監視しているだけなので、ノードが削除されると理由を判別する手段が失われる
- 結果として、受動側のUIは「相手にキャンセルされた」「拒否された」「正常終了した」のいずれであっても、同じ「オンラインに戻った」としか表示できなくなる

## 決定

`calls/{roomId}`を通話終了時に削除する変更は行わず、`docs/adrs/202609271801-call-room-schema-and-signaling-endpoints.md`の元の設計（`status: "ended"`・`endedReason`・`endedBy`・`endedAt`を書き込んで残す）を維持する。

削除しないことで生じる「レコードが増え続ける」問題は、`end` APIの同期処理の中で解決するのではなく、将来的に非同期のアーカイブ機構で対応することを検討する。想定している方向性は以下の通り。

- 定期実行（cron等）のバッチ処理が、`status: "ended"`かつ一定時間経過したレコードをログ・外部ストレージ（BigQueryやCloud Storage等）へ移してから、Realtime Database側のレコードを削除する
- 削除までに猶予期間を設けることで、通話終了直後のクライアントがRTDBから`endedReason`等を読み取る機会を奪わずに済む

## 理由

- 通話終了理由を受動側のクライアントにも伝えるには、少なくとも通話終了直後の一定期間は`calls/{roomId}`をRealtime Database上に残す必要がある
- レコードの増加に対する削除・アーカイブはクライアントの`end` API呼び出しに同期させる必然性がなく、非同期のバッチ処理に分離した方が「削除するタイミング」と「クライアントに終了理由を読み取らせるタイミング」という相反する要求を両立できる

## 影響・トレードオフ

- `calls/{roomId}`は当面削除されないため、`docs/adrs/202609271801-call-room-schema-and-signaling-endpoints.md`で指摘されていた「レコードが増え続ける」問題は本ADRの時点では未解決のまま残る
- アーカイブ機構（実行基盤、移行先のログ・ストレージ、削除までの猶予時間など）は本ADRの時点では未設計であり、別途の設計・実装が必要
